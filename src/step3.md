## **미션 배경**

예약 서비스는 여러 매장을 지원한다. 각 매장에는 매니저가 있다. 매니저는 자기 매장의 예약을 관리해야 하지만, 다른 매장의 예약을 수정하거나 삭제해서는 안 된다.

로그인한 사용자라고 해서 모든 예약에 접근할 수 있는 것은 아니다. 이제 인증을 넘어 인가가 필요하다.

3단계에서는 매장 매니저가 자기 매장의 예약만 관리하도록 제한한다.

## **목표**

- 인증과 인가를 구분한다.
- 로그인한 매니저가 어떤 매장에 속해 있는지 확인한다.
- 접근하려는 예약이 어떤 매장에 속해 있는지 확인한다.
- 매장 매니저가 자기 매장의 예약만 관리할 수 있게 한다.
- 인가 실패와 인증 실패를 구분해 처리한다.

## **요구사항**

### **매장 매니저 식별**

- 로그인한 사용자가 매장 매니저인지 확인할 수 있어야 한다.
- 매장 매니저가 어떤 매장을 관리하는지 확인할 수 있어야 한다.

### **예약 접근 제한**

- 매장 매니저는 자기 매장의 예약만 조회할 수 있다.
- 매장 매니저는 자기 매장의 예약만 변경할 수 있다.
- 매장 매니저는 자기 매장의 예약만 삭제할 수 있다.
- 다른 매장의 예약에 접근하려는 요청은 거부한다.

### **실패 처리**

- 로그인하지 않은 요청은 인증 실패로 처리한다.
- 로그인했지만 권한이 없는 요청은 인가 실패로 처리한다.
- 인증 실패와 인가 실패를 같은 문제로 뭉개지 않는다.

## **구현 조건**

- 로그인한 사용자가 어떤 매장에 속해 있는지 확인할 수 있어야 한다.
- 접근하려는 예약이 어떤 매장에 속해 있는지 확인할 수 있어야 한다.
- 두 정보를 비교해 요청을 허용하거나 거부한다.
- 인가 판단 로직이 컨트롤러에 과도하게 흩어지지 않도록 한다.

## **구현을 하며 선택해야하는 사항**

3단계의 핵심 선택은 “인가 판단을 어디에 두고, 어떤 정보로 권한을 확인할 것인가”다. 모든 교육생이 자기 매장 예약만 관리하게 만들어야 하지만, 그 판단을 코드 어디에 둘지는 선택이 갈릴 수 있다.

교육생은 다음을 직접 선택한다.

- 인가 판단 위치
  - 예: 컨트롤러에서 먼저 막을 것인가, 서비스에서 검증할 것인가, 도메인 객체의 규칙으로 표현할 것인가.
- 매장 매니저와 매장의 관계 표현 방식
  - 예: 매니저가 하나의 매장만 가지는 구조로 둘 것인가, 여러 매장을 관리할 수 있게 열어 둘 것인가.
- 예약 접근 권한 확인 방식
  - 예: 예약을 조회한 뒤 매장 권한을 비교할 것인가, 처음부터 권한 조건을 포함해 조회할 것인가.
- 인가 실패 응답 방식
  - 예: 권한 없음으로 응답할 것인가, 리소스를 숨기는 방식으로 응답할 것인가.
- 인증 정보와 도메인 정보의 연결 방식
  - 예: 로그인 사용자 ID로 매니저를 조회할 것인가, 로그인 객체에 매장 정보를 포함할 것인가.

공유회에서는 “권한 체크를 했는가”보다 “왜 그 계층에서 인가를 판단했고, 요구사항이 바뀌면 어느 부분이 흔들리는가”를 비교한다.

## **생각해 볼 점**

- 인가 판단은 컨트롤러, 서비스, 도메인 중 어디에 두는 것이 적절한가?
- 예약 조회와 예약 변경에서 인가 판단 위치가 달라질 수 있는가?
- 인가 실패 시 어떤 응답을 반환할 것인가?
- 매장 매니저가 여러 매장을 관리하게 되면 구조를 어떻게 바꿀 것인가?
- 인증된 사용자 정보를 인가 판단에 어떻게 전달할 것인가?

## **제출**

1단계, 2단계, 3단계 요구사항을 모두 구현한 뒤 하나의 PR로 제출한다.

최종 PR 설명에는 3단계와 관련해 다음 양식을 포함한다.

```
선택 도구:
다른 후보:
선택 이유:
인가 판단 위치:
유지하거나 변경하고 싶은 점:
```

## **완료 기준**

- 매장 매니저는 자기 매장의 예약만 관리할 수 있다.
- 다른 매장 예약에 접근하는 요청은 거부된다.
- 인증 실패와 인가 실패가 구분된다.
- 인가 판단 위치와 선택 이유를 설명했다.
